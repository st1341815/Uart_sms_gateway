# 新卡自检（Device Self-Check）设计方案

- 目标主机：`192.168.11.21`（dockersver），容器 `sms-multi`，镜像 `smstext-multi-device:1.4.3`
- 编写日期：2026-11-09
- 背景：新增第三张卡（`usb-0:1`）时，宿主机枚举正常但应用完全看不到。根因是「config.yaml 没写 + 容器 devices 没映射」。本次设计的目标是**让系统自己发现这类问题并给出可执行的下一步**。

---

## 一、目标与非目标

### 目标
1. 启动时 + 定期自检，回答四个问题：
   - 配置里写的每个 `Port`，在宿主机上还存在吗？
   - 每个已配置设备的串口，容器内真的打得开吗？
   - 宿主机上有没有**未被任何配置引用**的模块（= 新插的卡）？
   - 配置内部有没有冲突（ID 重复、两个设备抢同一个口、指向不存在的口）？
2. 发现问题时：界面有明确提示（含「下一步该干什么」）+ 可选通知推送（复用现有通知渠道）。
3. 不误报、不影响正在收发短信的设备。

### 非目标
- 不自动拨打、不自动发测试短信（会产生真金白银费用）。
- 不自动重建容器（重建会中断在跑的卡，必须是人来决定）。
- 不自动启用未知的境外卡（有国际漫游计费风险，参见 `sms-multi-analysis-r2.md` P0：未指定设备会随机选卡）。

## 二、现状约束（这四条决定了方案形态）

| # | 约束 | 证据 |
|---|---|---|
| C1 | 设备清单**只来自 `config.yaml` 的 `App.Serial.Devices`**，启动时读一次；Web 界面没有设备管理页 | `device_manager.go:188` 每台一条日志；`web/src/pages/` 只有 Dashboard/Messages/SerialControl/ScheduledTasks/NotificationChannels/OpenAPI |
| C2 | `config.yaml` 在容器内是**只读挂载**，程序写不回去 | compose `./config.yaml:/app/config.yaml:ro`；`device_manager.go` 注释明说改名只能落 properties 表 |
| C3 | 容器 `devices` 在**创建时固定**，不能运行时追加；未映射的节点在容器 `/dev` 里不存在 | `docker inspect` 显示 `ttyACM2 / ttyACM5`；新卡 `ttyACM6/7/8` 不在 `/dev`，`cat by-path` 报 No such file |
| C4 | 但 **`/sys` 与 `/dev/serial` 是宿主机的**，容器内能看到全部 9 个 ACM 与全部 by-path 软链 | `docker exec sms-multi ls /sys/class/tty \| grep -c ACM` → 9；`/dev/serial/by-path/` 9 条软链齐备 |

> C4 是本方案能"零运维改动"落地的前提：**容器虽然打不开未映射的口，但知道它们存在**。

另外一个实测规律（不是规范，只能当启发式）：每个 AirM2M 模块 3 个 ACM 口，程序用 **`:1.6`** 那个。

## 三、能力分层

### L0 · 一致性体检（零宿主机改动，强烈建议先做）
在容器内只读完成，不碰任何串口：

1. `readlink` 遍历 `/dev/serial/by-path/*`，取 `usb-0:N:M` 得到 **(USB 端口 N, 接口 M)** 与目标节点名。
2. 按 **端口 N** 分组 → 每个端口 = 一个物理模块（同型号 `19d1:0001`，SerialNumber 全是 `000000000001`，只能靠端口区分）。
3. 与 `config.yaml` 的 `Port` 集合比对：
   - **配置有、宿主机无** → `MISSING_ON_HOST`（卡被拔了 / by-path 变了）
   - **宿主机有、容器 `/dev` 无** → `NOT_MAPPED`（本次踩的坑）
   - **宿主机有、容器有、配置未引用** → `UNCONFIGURED`（新卡的 1.6 口）
   - **端口 N 完全没被任何配置引用** → `NEW_MODULE`（= 真的加了一张新卡）
4. 顺带校验配置本身：`ID` 重复、两台设备指向同一 `Port`、`Port` 不以 `:1.6` 结尾（可疑）。

**L0 能给出的结论**（本次案例）：
```
发现 1 个未配置模块：USB 端口 usb-0:1（AirM2M 19d1:0001）
  候选 AT 口：/dev/serial/by-path/pci-0000:07:1b.0-usb-0:1:1.6 → ttyACM8
  状态：宿主机存在，容器内 /dev 缺失 → 需要在 docker-compose.yml 增加 devices 并重建容器
三个已配置设备：sms1 正常 / sms2 正常 / sms3 正常
```
L0 拿不到运营商和号码（打不开设备），但**把"为什么看不到"说清楚**，这就是用户要的。

### L1 · 可探测（需要宿主机一次性改动）
让容器能真正打开新卡的串口，从而报出运营商/SIM 在线/信号，并能自动命名。

宿主机改动二选一：

**L1-a（推荐）容器侧自动建节点**
```yaml
    # docker-compose.yml
    security_opt:
      - no-new-privileges:true
    device_cgroup_rules:
      - 'c 166:* rwm'      # ttyACM 主设备号 166；放开整类，天然支持热插拔
```
镜像 entrypoint 加一段守护（需确认镜像 `USER=root`；Docker 默认带 `CAP_MKNOD`）：
```sh
# 每 10s 对齐 /sys 与 /dev：宿主机上有、容器里没有的 ttyACM 就建节点
while :; do
  for s in /sys/class/tty/ttyACM*; do
    n=${s##*/}
    [ -e "/dev/$n" ] && continue
    majmin=$(cat "$s/dev" 2>/dev/null) || continue
    mknod "/dev/$n" c "${majmin%%:*}" "${majmin##*:}" 2>/dev/null
    chgrp dialout "/dev/$n" 2>/dev/null
  done
  sleep 10
done &
```
> 不要用 `-v /dev:/dev`：它会盖掉 Docker 自己挂的 `/dev/pts`、`/dev/shm`，副作用更大。

**L1-b（不改镜像）宿主机 udev/hotplug 回调**
宿主机在插拔事件里把 `docker exec` 或 `docker cp` 做节点补齐。iStoreOS 走 `/etc/hotplug.d/` 不是 udev，维护成本更高，不推荐。

L1 拿到以后，探测流程（只针对未配置端口）：

```
for 每个未配置的 USB 端口 N:
    for M in [1.6, 1.2, 1.4]:                 # 1.6 优先，其余兜底试探
        打开 /dev/serial/by-path/...:N:M
        发一次状态请求帧（复用 RequestCacheUpdate 的协议）
        若 1.5s 内收到状态帧:
            解析 operator / online / iccid / imsi / csq
            AT 口 = 该 M，记录之
            成功返回，不再试下一个
```
只在未配置端口探测，**绝不动已配置设备的口**，避免把在跑的卡搞掉线。

### L2 · 自动注册（做完 L0+L1 之后才有意义）
新发现的模块自动落一条「待启用」设备：

- 存储位置：**properties 表**（`config.yaml` 只读，写不回去）。新增键：
  ```
  dyn_devices = {
     "usb01": {"name":"移动 138xxxx","port":"...:1.6","enabled":false,"source":"auto"}
  }
  ```
  启动时合并：`config.yaml` 静态设备（source=config）+ DB 动态设备（source=auto）。
- **默认 `enabled=false`**，界面显示为「待确认」，用户点「启用」才真正连串口。原因：未知卡可能是境外漫游卡，自动启用会让"未指定 device_id"的 API 调用落到它身上（历史 P0）。
- ID 用**端口派生**而不是递增序号：`usb01`、`usb02`…（同卡插同口 ID 不变，不因加卡顺序变号）。界面显示名可改（已有 `device_names` 覆盖机制可直接复用）。

## 四、方案对比与推荐

| 方案 | 内容 | 宿主机改动 | 能解决的问题 | 工作量 |
|---|---|---|---|---|
| **A** | 只做 L0 自检 + 界面卡片 + 通知 | 无 | 全都能报出来（含本次两张卡的老坑），但用户还得手工改 compose | 0.5~1 天 |
| **B（推荐）** | L0 + L1，能真探测并自动带出运营商/号码 | compose 加 `device_cgroup_rules` + entrypoint 守护（一次性） | 新卡插上后 10~60 秒内自动出现在界面「待启用」，可一键启用 | 2~3 天 |
| C | L0 + L1 + L2 动态设备表（界面增删设备） | 同 B | 彻底摆脱改 `config.yaml` | 5~7 天 |
| D | 宿主机 cron 脚本比对 by-path 与 compose，差异发飞书 | 只加脚本 | 运维告警，零程序改动 | 0.5 天 |

**推荐路线：A → B →（视需求）C。**
A 先落地能立刻止血（本次问题 100% 能被 A 报出来）；B 把"能不能用"也自动化；C 才是长期形态。

## 五、详细设计

### 5.1 后端

新文件 `internal/service/selfcheck_service.go`：

```go
type CheckItem struct {
    Level    string `json:"level"`      // ok | warn | error | info
    Code     string `json:"code"`       // MISMATCH_*/NEW_MODULE/CONFIG_DUP/...
    Message  string `json:"message"`    // 给人看的中文结论
    NextStep string `json:"next_step"`  // 可执行建议（命令 or 操作）
    Data     any    `json:"data,omitempty"`
}

type SelfCheckReport struct {
    GeneratedAt time.Time   `json:"generated_at"`
    Devices     []DeviceDiag `json:"devices"`   // 已配置设备逐台体检
    Modules     []ModuleDiag `json:"modules"`   // 宿主机枚举到的全部模块（按 USB 端口）
    Items       []CheckItem  `json:"items"`     // 问题清单
    Summary     struct {
        Ok, Warn, Error int
    } `json:"summary"`
}
```

关键函数：

| 函数 | 职责 |
|---|---|
| `scanHostPorts()` | 读 `/dev/serial/by-path/*`，解析出 `(usbPort, iface, target)` |
| `scanVisibleNodes()` | 列 `/dev/ttyACM*` + 对照 `/sys/class/tty/ttyACM*` → 区分 mapped / unmapped |
| `matchConfig(cfg)` | 与 `SerialConfig.Devices` 交叉比对，产出 CheckItem |
| `probe(port)` | （L1）打开串口发状态请求帧，解析 operator/online，AT 口探测 |
| `RunAndNotify(ctx)` | 启动跑一次 + 每 30 分钟一次；有新 error 才推送（带 6 小时静默窗口防刷屏） |

非容器环境（开发机直跑）时 `/dev/serial` 不存在 → 自动降级为只校验 config 与可见节点。

### 5.2 接口

```
GET  /api/serial/selfcheck            需要 JWT（和现有管理接口同级）
POST /api/serial/selfcheck/probe      仅 L1；对指定 usbPort 触发一次探测，限频 1 次/30s
```

### 5.3 前端

当前没有「设备」页，建议在 `SerialControl.tsx` 顶部加一张**自检卡片**（不新增路由，改动最小）：

- 三台设备行：名称 / 端口 / 连接状态 / 运营商 / 信号 / 结论徽标
- 「发现 N 个未配置模块」黄条，展开后：
  - 端口、候选 AT 口、`in_container` 布尔
  - 「复制 compose 片段」按钮：直接给
    ```yaml
    devices:
      - /dev/ttyACM8:/dev/ttyACM8
    ```
  - 「复制 config 片段」按钮：给出带实测运营商/号码的 `Devices` 条目
  - 提示文案固定模板：「改完执行 `docker compose up -d --force-recreate`，影响在跑的卡约 x 秒」
- 右上角「重新自检」按钮（对应 L0 只读接口，随时可点）

### 5.4 通知

复用 `notifier.go`，新增 property 开关（与现有 SIM 上下线通知同一套模式）：

| property key | 默认 | 说明 |
|---|---|---|
| `selfcheck_notify_enabled` | `false` | 发现新模块/严重问题时推送 |
| `selfcheck_notify_interval_min` | `360` | 同类问题静默窗口 |

文案示例：
```
[短信网关自检] 发现未配置模块
USB 端口 usb-0:1 · AirM2M · 候选 AT 口 ttyACM8（宿主机存在 / 容器内缺失）
处理：compose 增加 devices: /dev/ttyACM8 → docker compose up -d --force-recreate
```

### 5.5 宿主机侧（仅 B 期需要）

```yaml
# docker-compose.yml 追加
    device_cgroup_rules:
      - 'c 166:* rwm'
```
+ 镜像 entrypoint 加 mknod 守护（见 3.2）。同步更新 `docs/port-binding-by-path.md` 与 `README.md` 的"已知限制"段。

## 六、验收用例

| # | 场景 | 期望 |
|---|---|---|
| 1 | 插一张未配置的新卡（本次场景） | L0：60 秒内 `NEW_MODULE` + 候选 AT 口 + 复制片段；B 期：界面出现「待启用」并带运营商 |
| 2 | 拔掉已配置的卡 | 报 `MISSING_ON_HOST`，**不**误报为新模块 |
| 3 | 新卡在宿主机有、容器 devices 未映射 | 报 `NOT_MAPPED`，明确写"需要重建容器" |
| 4 | config 里两台设备写同一个 Port | 报 `CONFIG_DUP`，且不影响启动 |
| 5 | 容器未放开 cgroup（B 期改动前的旧部署） | 自检整体仍工作，探测项降级为 `UNSUPPORTED`，不报错 |
| 6 | USB 总线复位（插拔导致其它卡掉线） | 自检能报 `FLAPPED`（同一端口 10 分钟内 ≥2 次 up/down），并提示供电问题 |
| 7 | 探测未配置端口期间 | 已配置设备的日志无中断、无 `Serial port busy` |

> 用例 7 是硬门槛：探测必须只碰未配置端口。

## 七、风险与取舍

1. **`c 166:* rwm` 放开的范围**：容器能访问宿主机全部 ttyACM（这台专用机器上只有三张卡，实际影响可接受）。若不想放开，就只能走"逐节点 devices"，也就无法热插拔 —— 这是 A/B 两方案的根本分野。
2. **自动注册与"随机选卡"P0 的冲突**：L2 必须默认 disabled，且未指定 `device_id` 的 API 行为保持"拒绝或用唯一启用设备"，不能退回 Go map 随机。
3. **探测有副作用**：打开未配置口会让模块打一行 `usb serial disconnected` 之类的固件日志，不影响功能；但同一模块若已被别的程序占用会拿不到口 —— 探测失败要报"端口被占用"而不是"设备故障"。
4. **by-path 端口号会变吗**：`pci-0000:07:1b.0-usb-0:N` 里的 `N` 是物理口序号，插不同 USB 口才变；同一物理口重插不变。所以"端口派生 ID"是稳定的，但**换 USB 口 = 换 ID**，界面上要能改名。
5. **信息泄露**：自检返回 ICCID/IMSI/号码，接口必须和现有管理接口同级鉴权，不能落到 OpenAPI（AK/SK）那套对外通道。

## 八、建议排期

| 期 | 内容 | 参考工作量 | 交付判定 |
|---|---|---|---|
| A | L0 自检服务 + `GET /api/serial/selfcheck` + SerialControl 自检卡片 + 复制片段 + 通知开关 | 0.5~1 天 | 本次场景能被完整报出，且能一键复制修复片段 |
| B | compose `device_cgroup_rules` + entrypoint mknod 守护 + `probe()` 探测 + 「待启用」展示 | 1.5~2 天 | 新卡插上 60 秒内出现在界面并显示运营商 |
| C | 动态设备表（properties `dyn_devices`）+ 界面增删启用 + OpenAPI 设备选择器 | 3~4 天 | 不再需要手改 `config.yaml` 加卡 |

每期都走现有发布链路：本地 `npm run build` + `make prepare-embed` → 源码上传 `.21` → `Dockerfile.build` 出 `smstext-multi-device:<ver>` → 备份 compose → `up -d`，按 `pre-<ver>` tag 留回滚点。
